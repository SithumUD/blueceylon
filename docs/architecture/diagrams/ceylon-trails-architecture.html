Blue Ceylon · System Architecture

Distributed, event-driven tourism marketplace — 6 Spring Boot microservices on AWS ECS Fargate, RabbitMQ event bus, database-per-service (logical schemas) on single RDS, PayHere escrow payments, real-time STOMP notifications.

STATE 01Booking lifecycle (Booking Service)

PENDING→ CONFIRMED→ CHECKED_IN→ CHECKED_OUT ↳ terminal side-branches from PENDING / CONFIRMED: CANCELLED · REFUNDED — confirmation + availability decrement happen in ONE transaction with row-level locking.

STATE 02Fund lifecycle — escrow & payout (Payment Service)

INITIATED→ PENDING_GATEWAY→ COMPLETED→ HELD→ RELEASED→ PAID_OUT ↳ PENDING_GATEWAY → FAILED (webhook failure/cancel)  ·  HELD → ON_HOLD_DISPUTE (traveler refund form) → REFUNDED (admin approves) or back to HELD (rejected — hold clock resumes, never resets). ↳ RELEASED is the single payout gate: WHERE status = 'RELEASED' — refund and payout code paths are mutually exclusive by state, so the "refund approved vs payout ran" race cannot occur. held_until = check-out date (rooms) or last itinerary day (tours), frozen at confirmation.

PATTERNSKey engineering decisions developers must preserve

Database-per-service logical schemas

keycloak_db (owned by Keycloak) · catalog_db · booking_db · payment_db — isolated logical schemas on a single RDS instance to save cost. No cross-DB joins ever; cross-service reads use denormalized snapshots (e.g., hotelName on Booking) or Gateway API calls. Booking ⇄ Payment sync via events only.

Stateless JWT RS256, Keycloak-issued

Gateway is an OAuth2 resource server — verifies the RS256 signature at the perimeter against Keycloak's JWKS; downstream services trust forwarded claims + enforce @PreAuthorize AND resource-ownership ("does this owner own this hotel row"). No service stores a password or a signing secret.

At-least-once ⇒ idempotency

AMQP redelivers. Every consumer and the PayHere webhook handler must be idempotent (dedupe on bookingId / order_id). Poison messages route to DLQ after N retries. Payout + release cron jobs are safe to re-run — state only moves forward.

Escrow rule

Charge at checkout; never pay owners until the service date passes. Daily 00:15 release sweep, monthly (1st, 00:05) payout batch. Two-step: compute ledger, then disburse — a disbursement bug can't corrupt the source of truth.

Identity is Keycloak's job not ours

No hand-rolled password hashing, token issuance, or reset flows. Keycloak owns the credential store, hosted login UI, and RS256 signing keys; app services are OAuth2 resource servers that only ever read claims off a validated token. Business-domain data (which hotels a user owns, SLTDA guide status) still lives in each service's own DB, keyed by the Keycloak sub.

Soft delete + Flyway

@SQLDelete/@SQLRestriction — rows never physically deleted (audit, disputes, referential integrity). All schema changes are versioned Flyway migrations applied at startup.

Observability contract

correlationId minted at the Gateway, propagated via HTTP headers and AMQP message properties. Logs → CloudWatch. Health = Actuator /actuator/health (ALB + ECS). Notification autoscaling signal = queue depth, not CPU.

Approval model

Businesses create listings immediately; public visibility is gated on parent entity approval (parent.status = APPROVED). One admin decision cascades to all children — no per-listing queue. Hotel owners get Rooms + Tours; Agencies/Guides get Tours only.

Known gaps (do not treat as done)

  • No transactional outbox — MQ outage blocks publishes
  • WebSocket layer is single-replica until a backplane exists
  • CI has no test gate and no deploy job
  • Single payment processor; payouts are a ledger, not auto bank transfers
  • Internal escrow ledger ≠ licensed trust account (regulatory)
